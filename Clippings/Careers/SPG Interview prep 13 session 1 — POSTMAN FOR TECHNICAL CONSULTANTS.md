# POSTMAN FOR TECHNICAL CONSULTANTS

## Session 1 — What Is Postman?

Forget everything you've seen on YouTube.

For SPG...

Postman is simply:

> **A tool for testing APIs without using the application.**

Think of it this way.

Normally

```text
Retail Agent

↓

↓

↓

```

you remove Surefyre.

```text
Postman

↓

↓

↓

```

Now you know

whether the problem is

Surefyre

or

the API.

That's why consultants use it.

# Authorization

Most APIs need authentication.

Know these.

Basic Auth

↓

Username

Password

---

Bearer Token

↓

Authorization Header


> [!bearer token]-
> A bearer token is an **encrypted string or security credential that grants access to a protected web resource or API to whoever holds ("bears") it**, without requiring further proof of identity. It functions **like a concert ticket**: whoever has the ticket gets to enter.


> [!Authorization header]-
> An Authorization header using a Bearer token is the standard HTTP mechanism used by clients to authenticate API requests. Defined in RFC 6750, it allows a client to prove its identity by simply "bearing" (holding) a security token generated by the server.


API Key

↓

Secret Key

---

OAuth

↓

Token

Refresh Token

You don't need to implement OAuth.

Just recognize it.


> [!OAuth2]-
> OAuth 2.0 is the industry-standard protocol for authorization. It lets a website or app access data on another service on behalf of a user without sharing the user's actual password. It uses temporary tokens and explicit permissions instead

# How do you use Postman?


> [!Postman]-
> Postman is a popular software platform used by developers and testers to build, test, share, and manage APIs (Application Programming Interfaces). It provides an easy-to-use graphical interface to send web requests, view server responses, automate tests, and collaborate with team members.

If asked

How do you use Postman?

I'd answer

> I primarily use Postman as an independent **API testing and troubleshooting tool**. It allows me to verify whether **issues** originate **in the application, the request payload, authentication, or the downstream service**. 
> 
> I organize **requests into collections**, use **environment variables to switch** between Development, QA, and Production **environments**, and **validate both request and response payloads** to support implementation and troubleshooting.

That's a very strong answer.

# POSTMAN CHEAT SHEET

| Postman Feature       | Why Consultants Use It                                      |
| --------------------- | ----------------------------------------------------------- |
| Collections           | Organize API requests by project or workflow                |
| Environment Variables | Switch easily between Dev, QA, and Production               |
| Variables             | Reuse values such as IDs and tokens across requests         |
| Headers               | Set content type, authorization, and other request metadata |
| Authorization         | Test API authentication (Basic, Bearer, API Key, OAuth)     |
| Body                  | Send JSON payloads to the API                               |
| Response              | Verify returned data and status                             |
| Tests                 | Validate expected API behavior automatically                |

> [!Swagger vs Postman]-
> ==**Swagger** is a set of open-source tools built around the OpenAPI Specification (OAS) used to design, describe, and document RESTful APIs. **Postman** is a comprehensive API platform used for testing, building, modifying, and collaborating on APIs==.
> 
> The primary difference is that Swagger focuses heavily on **API design and documentation**, while Postman focuses heavily on **API testing and development workflows**.
